实验12 persona 遮蔽与 persona 税

实验设计
  • 控制组为宿主 $PROFILE/cordis.patch.yml 的 system-prompt.personaPrefix（七段纪律，含已过期内容）；实验组为 bundle persona.md 的 15 节化用层（三模式 persona.prefix）。观测指标为两侧字符数、会话系统提示中谁出现、标题撞名与合法重叠串、以及 ptc 下 persona 与工具面的指向一致性。扰动：无注入（纯文本层对账）。
执行数据
  • 来源 evidence/a12-persona-scope-evidence.json（inputs 记 bundle cordis.patch.yml sha256 6e903497…、persona.md sha256 f39ce841…、宿主 patch sha256 70efba5e…）、evidence/persona-behavior-markers.json；运行时取自四份会话日志的装配后系统提示全文（E1 复算）；源码级机制核对 $DSH/packages/preset/persona/src/index.ts:1-14,62-68（文件头注释：mounted inside an agent preset it *shadows the deployment persona* for that one session）与 tests/persona.spec.ts:32；时间戳 2026-10-11。
观测结果
  • 宿主 personaPrefix = 2790 字符 / 8 小节；bundle persona.md = 8018 字符 / 15 节（≈3084 tokens）；内置 standard 的 persona.prefix 仅 54 字符。四份会话系统提示中，判别串「成本意识」「MEMORY 硬门禁」「联网代理纪律」全为 false → 宿主七段纪律在所有会话都不生效，被 preset 的 persona 行遮蔽（机制与源码一致：preset persona 与宿主注册同名 section deployment:persona-prefix，后者被替换）。系统提示字符数：内置 standard 5594 / 三模式 13658（15 小节齐备、0 命中禁用字面量 [GATE]/Ctrl+T/variant/http_proxy）/ ptc 53826（+40168，来源是 run_code 的内联 SDK 与工具说明）。两侧存在标题撞名 委派纪律/留档规范/编码安全，与合法重叠串 reflection_add、dsh-v0.2.1-alpha.2（已登记，非泄漏）。宿主那份含过期内容（「默认模型为 opencode-go/deepseek-v4-flash，deep 变体留给 ≥13 分场景」），与本机实际默认模型 opencode-go-tmp/deepseek-v4.1-flash 不一致且 DSH 无变体概念。ptc 空指向：persona.md:26 写「本模式提供 subagent（通用）、oc_explore…不要一律用 subagent」，而这些名字在 ptc 顶层工具目录里不存在，persona 未按 presentation mode 分支。
量化指标
  • persona 字符 2790（宿主）→ 8018（bundle，×2.87）；系统提示 5594 → 13658（×2.44）→ 53826（×9.62）；persona 税 ≈ +8064 字符/请求（三模式）、+48232 字符/请求（ptc，约 +40 KB）；宿主纪律生效 0/4 会话（遮蔽率 100%）；标题撞名 3 处、合法重叠 2 处、过期条目 1 条；ptc 空指向 1 处（§二 worker 清单）。
控制论解读
  • 属 M 环（状态/上下文预算）+ E 环（配置态可观测性）。控制律为「同层覆盖（shadowing）」：persona 是每个请求都要付的固定上下文税，遮蔽让宿主纪律从「活配置」变成「死配置」——不生效但仍留存在文件里，形成隐藏状态（未生效的分支），这正是 M 环最怕的「状态估计与实际不一致」。风险不在于税本身（8018 字符换 15 节行为纪律，性价比可接受），而在于无 preset 的回落路径：一旦某会话不挂 preset persona（换 profile / preset 行被禁用 / 挂载失败回落），这份含过期模型的七段纪律会突然生效并与现行 persona 并存冲突——判据层应把「宿主 personaPrefix 是否被遮蔽」做成可观测项，而不是靠人记得。ptc 的 53826 字符则是税与收益脱钩的极端样本：上下文成本涨到 9.6 倍，而 persona 的指令形状（"调用 X 工具"）与 ptc 的"只能直接调 run_code"不一致，模型必须自行翻译——同一份 persona 在不同 presentation mode 下的语义有效性不同，属装配层的隐性不一致。

实验13 bundle 门控假阳性与修复（判据脆性）

实验设计
  • 控制组为 bundle 自家门控 verify_bundle.py 的历史 PASS 记录（README §8 验收表 + evidence/verify-bundle-13checks.out.txt）；实验组为新鲜复跑同一门控。观测指标为 13 项检查的逐项结论、FAIL 项的报错原文、漂移根因的可复算证明、修复后复跑结论。扰动：外部无关联扰动——宿主 patch 被 GUI 写回一行 UI 偏好（ui-theme.fontSize: 16），与 bundle 无任何因果关系。
执行数据
  • 复跑命令 PATH=<nvm-bin> python3 $BUNDLE/verify_bundle.py（$BUNDLE=/home/zako-mio/.dsh/presets/opencode）；根因反推用「删行重算 sha256」：把宿主 patch 中该行删掉后重算 = 70efba5e6873a60ed1480e5f9a6eb0d83faaaa8d95344ebc2fc5dffec25339b4，与 provenance.json / a12-persona-scope-evidence.json 记录值完全一致（MATCH）；宿主 patch mtime 2026-10-11 05:55:08（晚于 A12 取证 05:39）；修复动作 = build_provenance.py 指纹口径由整文件 sha256 改为 scoped_digest（只取 bundle 实际消费的字段 system-prompt.personaPrefix），随后重跑门控与 build_provenance.py 并重新生成验收证据文件；时间戳 2026-10-11。
观测结果
  • 新鲜复跑第 11 项 FAIL，报错原文 provenance drift: 八、环境事实: source drifted (70efba5e6873 -> 9c00a1a14339)；前 10、12、13 项 PASS。根因经 sha256 反推锁定为宿主 patch 被 GUI 写入一行 ui-theme.fontSize: 16（用户调字号），与 bundle 内容无关 → 假阳性。修复后 verify_bundle.py 13/13 PASS，验收证据文件重新生成。附带事实：verify_bundle.py 唯一写操作是 tempfile.TemporaryDirectory() 内的 rows.json（:389-391），不污染仓库，可安全复跑。
量化指标
  • 门控项数 11 → 13 项（本轮新增 check 13 = A12 取证）；复跑前 PASS 12/13（第 11 项 FAIL）；修复后 PASS 13/13；漂移根因定位置信度 = MATCH（sha256 精确等于记录值，非近似）；被误纳判据的无关字段 1 个（ui-theme.fontSize）；修复后判据作用域 1 个字段（system-prompt.personaPrefix）；假阳性触发概率 = 任意一次 GUI 偏好写回（高频）。
控制论解读
  • 属 E 环（传感器/验证器）自身的可信度——是「对传感器的传感器」。控制律本应是「源漂移 → 报警」，但判据把与 bundle 无因果关系的整文件字节纳入观测面，等价于给传感器接上了一个高噪声信道：宿主 GUI 每次写回都注入一次扰动，于是门控红灯的语义被稀释。这是假阳性比漏报更贵的典型——它会训练使用者忽略红灯，最终把真漂移一起放过（噪声淹没信号，E 环信噪比崩塌）。修复的实质是把判据从「文件指纹」下沉到「被消费字段指纹」：观测面必须等于因果面，判据须绑被消费字段而非整文件指纹。修复后仍保留上游漂移检测能力（plan-mode section 的覆写源仍在指纹覆盖内，见实验11 的 Δ4），即降噪未牺牲灵敏度。

执行数据

观测结果

量化指标
  • 可逆性 4/4 阶段通过（干跑/安装/卸载/重装）；既有 preset 区域字节差异 = 1 行注释（0 处语义变更）；插件计数 188 → 191 → 188（净 Δ = +3，卸载后归零）；权限档 3 → 5 → 3；重装后组合树与首次安装后逐字节一致（差异 0）；备份件 ~/.dsh-backups/opencode-port-20261011/ 1 套。
控制论解读
  • 属 T 环（执行器）+ R 环（闭环可逆性），是「受控可逆性」这一实验红线的正面样本。控制律为「先干跑（前馈预测）→ 再应用（执行）→ 每步自带验收（传感）→ 可回滚（反向执行器）」的四段式，等价于给装配动作加双向执行器 + 状态快照：卸载只移除自己的三行、既有区域零语义变更，说明 bundle 的作用域是封闭且可判定的（没有"改一处、坏一片"的耦合）。「重装后逐字节一致」比「卸载干净」更强——它同时证明安装是幂等的（同输入同输出，无隐藏状态累积），这是把装配层当控制器时最关键的稳定性性质：可回滚 ≠ 可重放，本实验两者都测了。唯一留档风险是 L18 已自述的不可移植性（persona 含本机绝对路径、node_modules 28 个符号链接指向本机源码树）：在本机可逆，换机即失效——可逆性的成立以环境不变为前提。

整体控制论结论
  • dsh-custom 的本质是「强内核 + 薄装配层」——与 opencode-custom 的「弱内核 + 强装配层」恰好互补。内核已自带 T 环硬约束（沙箱档位 fail-closed、spill 限幅、session 事件溯源）与 M 环基础设施（append-only session + compaction + FTS5 检索），装配层因此不需要补内核，只需补编队（具名 worker + oc_* 别名）、策略库（45 派生 skill）与行为纪律（persona）三件事；实验11 证明这三件事的可见性边界是干净的（纯净模式 31 工具 / 0 skill，零污染）。真正的薄弱点不在内核也不在编队，而在装配层的两个语义接缝：① 遮蔽造成的隐藏状态（实验12：宿主 2790 字符纪律 100% 不生效却仍留存，回落路径上会突然复活且含过期内容）；② 判据的观测面大于因果面（实验13：整文件指纹把 GUI 偏好写回误判为源漂移，E 环信噪比被稀释）。实验14 则给出正面证据：装配动作本身是封闭、幂等、可双向执行的（卸载零语义外溢、重装逐字节一致），说明「可逆性」这一红线在本装配层上是可工程保证的，而非口头承诺。综合判据强度梯度（沿用 opencode-custom 的结论框架）：运行时硬阻（沙箱档位 fail-closed）> 确定性脚本门控（verify_bundle.py，但作用域必须收紧）> 声明层（toolFilter 行）> 纯提示词（persona 纪律）；建议后续把 persona 的「按 presentation mode 分支」与「遮蔽态可观测」两项下沉为声明层或门控项，避免 M 环隐藏状态长期累积。 > 口径：仅登记已取证的损失，分「不可实现 / 行为落差 / 风险」三类；未取证项不登记。
