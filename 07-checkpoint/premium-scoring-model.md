# 精装房评分模型（硬门槛 + 8 维加权 + 一票否决）

> 版本：v2.0（评分模型化）　创建：2026-09-08　对标：`0907-笔记本选购全流程/01-调研证据与指标体系.md` §9
> 单一数据源：`09-src-data/premium_scores.py`（分值只此一处，生成物全部由此派生）

---

## 一、为什么要把主观评分改造成模型

旧版精装度（`premium-diff-analysis.md` §一）是**单点 0-5 打分**：以「用户零配置跑端到端」为锚点，
由分析者凭证据直接给一个总分。问题有三：

1. **不可复核**——同一份证据，不同人给的 5 分 / 4.5 分无法对账，缺分解依据。
2. **维度混淆**——「有沙箱」和「有 7 万 Skills」对"开箱即用"的贡献被压成一个数，权重隐含且不可见。
3. **声称污染**——营销声称的能力直接进入总分（如 Windsurf Flows DAG），「声称 ≠ 实际」的命题在评分层面失守。

本模型把评分拆成**三层结构**，与笔记本选购法同构：

| 层 | 机制 | 作用 | 笔记本法对应 |
|----|------|------|-------------|
| 第 1 层 | **硬门槛前置（0/1，不计权重）** | 先判「能不能零配置跑端到端」，不达标者降档封顶 | 显存 ≥12GB 前置筛选 |
| 第 2 层 | **8 维加权（合计 100%）** | 达标者在 8 个可量化维度上加权求综合分 | 散热/性价比/口碑等加权 |
| 第 3 层 | **一票否决** | 声称失实 / 纯中转无底座 → 直接封顶，禁止进入高精装档 | 散热崩/售后拒修一票否决 |

---

## 二、第 1 层：硬门槛（0/1，不计入权重）

### 定义

> **端到端可跑门槛**：用户**零配置**（仅允许填一次 API Key / 选一次模型）即可跑通一个**端到端任务**
> （下达目标 → Agent 自主拆解 → 调用工具 → 产出交付物），无需编写角色/流程代码、无需自建底座、无需外部客户端配合。

| 判定 | 含义 | 处理 |
|:---:|------|------|
| ✅ PASS | 自足成品，注册/安装即可跑端到端任务 | 进入 8 维加权 |
| ❌ FAIL | 需写代码/填流程/依赖外部客户端或第三方底座才能跑通 | 综合分**封顶 3.0**（"需装修"档），并降档标注 |

### 判定结果（14 产品）

| 产品 | 门槛 | 判定依据 |
|------|:---:|------|
| OpenHands / Devin / WorkBuddy / Dify / OpenClaude / Cursor / Coze / Windsurf / GPT-Researcher / CodeWhale / Copilot | ✅ | 安装或注册后即可跑端到端任务（详见各画像"一键部署"维） |
| **CrewAI** | ❌ | 框架：必须由用户编写角色/任务/流程（`crewai create crew` 仅给脚手架），非零配置即用 |
| **QCode** | ❌ | 纯 API 中转：自身无 Agent 能力，必须配合外部 Claude Code 客户端 |
| **CC-Router** | ❌ | 纯路由/中转：自身无 Agent 能力，必须配合外部客户端与第三方网关 |

> **注**：门槛判的是「能否零配置跑端到端」，与「安装难度」不同。CodeWhale 用 cargo 构建（部署维仅 3 分），但构建后即可端到端跑任务，故门槛 PASS。

## 三、第 2 层：8 维加权（合计 100%）

### 3.1 权重表与设计依据

权重按「对开箱即用的贡献度」分配——越靠前的维度，用户越是"没有它就跑不起来"：

| 维度 | 权重 | 设计依据 |
|------|:---:|------|
| **多Agent编排** | 16% | 精装房的核心卖点：能否自主拆解/并行/委派。缺失则退化为"单轮问答"，是成品与框架的分水岭 |
| **一键部署** | 15% | 门槛层判"能不能跑"，本维判"跑得多省事"（SaaS 注册 / 单命令 / 源码构建），决定首次成功体验 |
| **模型接入** | 14% | Agent 的燃料；开箱多 provider / 一键换模型，否则用户卡在接入 |
| **工作流** | 13% | 端到端任务的编排骨架（可视化画布 / DAG / 触发自动化），决定"能否稳定复现任务" |
| **Skill库** | 12% | 预装能力密度：技能市场 / 插件库 / 内置工具集，决定"不写代码能干什么" |
| **沙箱** | 10% | 安全执行隔离；缺失不阻断使用，但限制自主执行的边界与信任度 |
| **MCP生态** | 10% | 开箱可扩展性；MCP marketplace / 多传输决定"接外部世界"的成本 |
| **记忆** | 10% | 跨会话连续性；缺失影响长任务与个性化，但不阻断单次任务 |

> 合计 16+15+14+13+12+10+10+10 = **100%**。
> 「一键部署」同时出现在门槛层与加权层：门槛层是 0/1 的"能否端到端跑"，加权层是 0-5 的"部署体验成熟度"，二者正交（同如笔记本"显存门槛"与"性价比加权"的关系）。

### 3.2 每维 0-5 评分标准（可量化、可复核）

| 分 | 多Agent编排 | 一键部署 | 模型接入 | 工作流 | Skill库 | 沙箱 | MCP生态 | 记忆 |
|:--:|------|------|------|------|------|------|------|------|
| **5** | 内置多 Agent + 并行 + DAG/委派，开箱可用 | 托管 SaaS 注册即用，或单命令 docker/npm 起 | 200+/千级模型或多 provider 预设，开箱 | 可视化画布 / 真 DAG + 自动化触发 | 大型技能/插件市场或 7 万+ skills | per-session 独立 VM / OS 级沙箱 | MCP marketplace + 多传输 + 一键安装 | 跨 session 知识库 + 长期记忆 + 结构化状态 |
| **4** | 多 Agent 并行/委派，但无真 DAG 或受限 | 一键安装/脚手架，少量配置 | 多模型 + 自动路由 | 工作流编排 + 触发，需配置 | 官方技能库/插件市场 + 内置工具集 | 容器隔离 / ephemeral 环境 | 内置 MCP + 多传输 | 记忆 + 知识库 + 持久上下文 |
| **3** | 多 Agent 原语/可配置，需用户编排 | 标准包管理安装 + 配置 | 多 provider，需填 key/配置 | 编排原语/脚本，需用户搭建 | 内置工具集/部分 skills，非市场 | 审批阀门 / 权限控制，非完整沙箱 | MCP 接入 / 工具节点 | 会话级 + 部分持久 |
| **2** | 仅单 Agent 或极弱多 Agent | 源码构建 / 自建 | 单/少数模型 | 弱编排 | 少量工具 | 平台侧隔离（未实证） | 依托上游 / 未明确 | 仅会话 |
| **1** | 名义多 Agent | 复杂自建 | 需自接 | 几乎无 | 几乎无 | 名义隔离 | 宣称支持无实证 | 几乎无 |
| **0** | 无 | 无 | 无 | 无 | 无 | 无 | 无 | 无 |

> 每维取值均以画像 MD「预装能力清单」的 ✅/部分/✖️ 与证据为依据；同一证据在不同维取同档，避免主观漂移。

## 四、第 3 层：一票否决

一票否决 = 无论加权分多高，触发者**封顶降档**并强制标注。本库两类触发：

| 触发类型 | 定义 | 封顶 | 触发产品 |
|------|------|:---:|------|
| **声称功能不存在** | 官方/流传声称的核心能力经实证**并不存在** | **4.0** | **Windsurf**（声称 Flows DAG 多Agent编排；实证为 Arena + worktrees + Managed Devins） |
| **纯中转无自研底座** | 核心能力建立在第三方网关/上游 API 之上，无自研 Agent 底座 | **3.5** | **QCode**（官方价×服务倍率）、**CC-Router**（依赖 `@the-next-ai/ai-gateway`） |

### 触发影响说明

- **Windsurf**：加权原始分 4.56（8 维中 6 维满分），但「多Agent编排」声称的 Flows DAG 不存在 → 该维按实证计 3 分，且综合分封顶 4.0。**否决使其从"真·开箱即用"档降入"成品化受限"档**。
- **QCode**：加权原始分仅 1.36（无多Agent/工作流/技能/沙箱/记忆，仅模型接入 4 + 一键接入 4 + MCP 依托 2）→ 封顶 3.5 与门槛封顶 3.0 均不触及，最终 1.4。**否决+门槛共同确认其"中转"本质，而非 Agent 成品**。
- **CC-Router**：加权原始分 2.06（无多Agent/沙箱/记忆，技能/工作流各 2）→ 门槛封顶 3.0，最终 2.1。**否决确认其"路由中转"本质**。

> 与笔记本法"直接淘汰不计分"不同，本模型对触发者**保留在矩阵内但封顶降档**——因为 14 产品全景的交付目标是"对照谱系"，淘汰会使谱系断裂。此为对笔记本法的**适配性调整**，已在本文档显式声明。

## 五、综合分公式

```
raw(slug)   = Σ (权重_k × 维度分_k) / 100            # 8 维加权，0-5
final(slug) = round( min( raw, 门槛封顶(若 FAIL=3.0), 否决封顶(若触发) ), 1 )
```

`门槛封顶` 与 `否决封顶` 均为**上界**（取 min），二者同时触发时取更严者。

## 六、模型与笔记本法的对标表

| 环节 | 笔记本选购法 | 本精装房模型 |
|------|------|------|
| 前置硬门槛 | 显存 ≥12GB（0/1，不计权重） | 端到端可跑（0/1，不计权重） |
| 加权维度 | 散热25/性价比22/口碑18/内存12/CPU10/扩展8/屏幕5 | 多Agent16/一键部署15/模型14/工作流13/Skill12/沙箱10/MCP10/记忆10 |
| 一票否决 | 散热崩/蓝屏/售后差/批次质量门 → 淘汰 | 声称失实（封顶4.0）/ 纯中转无底座（封顶3.5） |
| 处理方式 | 直接淘汰不计分 | **保留并封顶降档**（适配全景对照需求） |
| 单一数据源 | 指标表 | `09-src-data/premium_scores.py` |
