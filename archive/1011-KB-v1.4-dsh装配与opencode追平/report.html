5. 反思 / 分析 / 建议

5.1 方法论层面的三条收获

  • 「数量下降 ≠ 能力下降」需要显式登记。本轮 opencode-custom 的 agent 10→9、MCP 6→4 都是结构调整（drawio/vision 退役、制图改走 skill 档位），若只报增长就是选择性叙述；本轮把 L1 视觉代看退役 / L2 MCP 工具面收窄 两项损失写进画像、diff、门控结果与报告四处。⇒ 复评必须同时登记「增」与「损」，否则「维持分值」会显得像没查。
  • 同一装配层跨宿主迁移会出现「能力掉队」，且掉队点是可定位的。opencode 侧 architecture-judgment 门控栈判「E 环反转」（子 Agent 有 bash 可自跑门控）；迁到 dsh 后子 Agent 无 bash ⇒ 门控无法在产出方自跑，E 环只判「增强」；R 环更因 dsh-reflection 插件移出而完全断裂。⇒ 迁移工程的验收判据不能只看「组件是否齐」，必须看每个组件的运行时前提是否满足。
  • 判据要绑「被消费字段」而非「整文件指纹」。bundle 自家门控第 11 项曾因宿主 patch 是活文件（GUI 写回字号即漂移）而假阳性 FAIL——假阳性会训练人忽略红灯，比漏报更隐蔽。⇒ 判据的作用域必须与「实际会被消费的面」对齐（与既有的「公式层比数值层更深一层」同源）。

5.2 环境与流程层面的建议

  • 「环境限制应转成可复现的代码，而非一次性绕过」：DAG 的 headless 脚本原先写死 snap chromium；本轮改为 detect_browser() 自动探测后，两种环境都能跑。建议把该模式推广到所有依赖外部可执行文件的脚本。
  • 子 Agent 无 bash 是当前架构的硬约束，由此形成稳定的分工范式：子 Agent 写（内容/代码）、主 Agent 跑（脚本/门控/git）。建议把该范式写进 opencode-capability-extension 的委派章节，避免后续轮次重复试错。
  • 覆盖率清单必须入库：v1.3 的 79 项清单落在 /tmp，本轮已改为入库的 112 项显式期望清单 + 派生脚本。建议后续轮次只改清单、不改门控逻辑。
  • 快照必须自带时间戳：本轮实测到「同一会话内 skill 数 45→46」的实机漂移；collected_at 让「口径以哪一刻为准」可判定，而不是靠事后推断。
  • 跨库交叉验证有额外收益：本轮把 dsh 侧 1010 遗留的「网关 MissingSessionID 未归因」与 opencode v1.18.34 的 release note 对上，闭合了一条悬了一个月的证据链。建议在复评流程里固定一步「跨库悬案回填」。
