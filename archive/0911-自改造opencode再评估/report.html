5. 反思 / 分析 / 建议

5.1 诚实口径（本轮最重要的纪律）

复评的价值不在于「分数又涨了」，而在于如实判定未跨档位。装配层一年来机制累积显著（三层栈、能力扩展 SOP、7 个新 skill），但评分模型的分档锚点是「产品化阈值」（可视化画布、插件市场、数百模型开箱、一键分发、VM 沙箱），这些锚点未变，故官方 2.9 / 自改造 3.9 维持不变，只在画像/diff 刷新 evidence 与机制叙述。此举把「机制增多」与「产品档位跃迁」解耦，避免用增量叙事掩盖分档口径，是复评可长期保持可信的关键。该口径已固化为契约 §2.7「诚实口径」条款。

5.2 实验10 暴露的治理问题（提示词级 vs 权限层）

实验10 显示：MEMORY 硬门禁条款齐备（auto-mode.md 子Agent 通用规则 + build prompt 双条款）、唯一写入链路 5 环节完整（封装→pending→worker→确认→签名写入），但 opencode.jsonc 为 /reflection 放行的 MEMORY edit allow 覆盖 6/13 agent 定义（含 build），使「唯一例外」在权限层成为制度化旁路。由此得出治理强度梯度：运行时硬阻（gate 脚本确定性二值判定）> 半运行时（权限 allow/deny）> 纯提示词（GATE / MEMORY 门禁）。建议把关键门禁从提示词层下沉到 runtime/权限层（如将 MEMORY 写权限收敛到专用 /reflection 执行上下文）。

5.3 边界与遗留（如实披露）

  • DAG 内部结构沿用 v1.18.29 基线：官方 v1.18.30 未重算内部模块 import，节点页内部结构 DAG 与 08-collect/internal-v1.18.29.json 均为 v1.18.29 基线，已在节点页与 README 显式标注「v1.18.30 结构未变」。若后续版本涉及跨模块 import 变化，须重跑 s1-parse-internal.py。
  • 08-collect 中间数据版本串：stage-00-version-baseline.json 与采集脚本的版本串仍为 v1.18.29，指向 v1.18.29 worktree；结果因结构未变而正确，但版本串与标注分叉，建议下轮统一。
  • drawio MCP 超时：不影响交付，但暴露单点脆弱，建议导出步骤加超时重试 + PNG bbox/尺寸双重校验。
  • 能力扩展 SOP 模板落点漂移：建议以 local-bindings.json 一类绑定声明替代硬编码的 <MISSION_ROOT> 占位路径。
  • 实验10 为静态验证：子Agent 动态拦截探针受记忆系统写红线限制未做，结论以静态条款与权限面审计支撑。

5.4 建议

  • 把门控期望值改为数据驱动：DAG 的节点/组/装配/外部/机制计数宜从 modified-dag.json.stats 动态读取，减少硬编码手改遗漏（本轮唯一 FAIL 来源即硬编码 119）。
  • 单一真相源派生：以统一 version 常量派生所有脚本路径与输出文件名，配合一次引用普查，根治「数据与标注分叉」。
  • 关键门禁下沉：优先将 MEMORY 写权限收敛到专用执行上下文，把提示词级门禁升级为看门狗级硬限幅。
  • 变体复评常态化：按契约 §2.7 触发条件（官方基线漂移或装配层能力纵深增长）定期复评，每次以「是否跨档位」为准绳，维持不虚报纪律。
