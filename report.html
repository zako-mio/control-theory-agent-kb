1. 当时情况

用户提出将控制理论核心思想深度融入 Agent 设计与开发，形成系统知识库。用户描述从「调参工程师」进化为「系统架构师」，用负反馈闭环/状态估计/PID/鲁棒控制/分层控制五个维度重新定义 Agent 设计。

要求联网检索权威知识（官方优先、多源交叉验证），分析 6 个真实 Agent 产品（opencode/deepseek-harness/PRIME/hermes/claude-code/codex）作为应用案例，形成「人类可读 + AI 友好」双线知识库，最后完成一轮自审阅。

2. 制定计划

核心决策（grill-me 收敛，11 项全对齐）：

  • 业务需求驱动（控制理论作技术工具库，非理论全集灌输）
  • 价值主张 = Agent 系统设计框架 + 大规模实验落地
  • 框架骨架 = 五大核心环全覆盖（M记忆/P规划/R反思/T工具调用/E评估）
  • 权威策略 = 分类型差异化（理论 ≥2 权威源；案例一手观察+源码）
  • 实验主线 = 全产品标准实验组（正常/故障注入/上下文污染/超长循环）
  • 交付形态 = 双线（人类端交互 HTML + AI 端结构化 MD + 契约）
  • 自审 = L1-L7 分层门控全验；实操授权 = 完全授权 + 破坏性前置问（最小必要范围）

推进节奏：先 3 样板打通 → 验证形态 → 铺开 3 产品 → 完整 6 产品终态。

3. 执行情况

委派情况（核心方法 = 主 Agent 编排 + 子 Agent 执行）：

  • Phase 1：5 路 search-worker 并行检索 31 知识点；补强 3 个 S1 弱项（LQR/反饱和/分层控制）+ 回源纠正 2 处可疑 DOI（Zames/Doyle）
  • Phase 2：Software Architect 角色 general 子 Agent 构建五环映射框架
  • Phase 3：6 路 explore 并行做控制论画像（3 本地源码 + 3 clone）
  • Phase 4：opencode 实机受控实验 + 5 产品源码可逆注入点分析
  • Phase 5：主 Agent 构建双线交付（根 index + 19 页 HTML 集群 + AI 索引 + 2 drawio 图）
  • Phase 6：三层门控（结构脚本 + VLM 视觉 + headless 渲染）

遇到的问题及应对：GitHub API 限流→改用 git ls-remote；PRIME 仓库定位困难→webfetch 定位；/tmp 混入检索残留→清理+备份；opencode 装配层干扰→用 --pure；1 个非法临时 JSON→清理后门控通过。

核心成果/洞察（6 产品对比）：

  • T 环（执行器）是 6 产品共同最强环——看门狗/限幅/沙箱是 Agent 工程最成熟环节
  • E 环（评估）从样板三产品「一致最弱」分化为两派——hermes 有独立 Critic、codex 有双评审器，E 环变强；opencode/dsh/PRIME/claude-code 仍弱
  • 「E 环最弱」是早期产品共性，非 Agent 普遍规律——成熟产品已把独立评审器作为一等公民
  • 各产品最弱环分化：opencode/dsh/PRIME/claude-code = E；hermes/codex = P
  • M 环普遍缺置信度（P 协方差）——记忆多记事实不记"我有多确定"

5. 反思/分析/建议

过程反思：委派协议显著提效（6 路并行检索/画像，31 知识点 + 6 画像在有限轮次完成）；契约先行（contract.md）后后续子 Agent 引用短路径，避免长 prompt 截断，KT 互引校验全部通过。

收获认知：分类型差异化权威策略正确——理论类（≥2 权威源）+ 案例类（一手观察/源码）分离，高危数据强制回源（Zames/Doyle DOI 回源纠正是关键动作）。三样板「E 环最弱」结论在补齐 3 产品后被修正为「分化两派」，说明单一样本结论易过拟合，需跨样本验证。

未来改进建议：

  • E 环「达标评估」是最大设计缺口——建议专题研究如何为 Agent 设计独立 Critic/验证器（理论支撑 KT-ctrl-006/035）
  • M 环置信度建模——引入「状态 + 置信度」双量（P 协方差类比）
  • hermes/codex 的独立评审器（Guardian/Review + confidence_score）是最佳实践模板
